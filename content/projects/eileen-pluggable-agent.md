## 问题

大多数 agent 产品是"一个聊天框接一个模型"。但真实的个人工作流跨越多个场景：手机上随手收集灵感、桌面上处理本地文件、云端长期运行任务。单一形态的 agent 接不住这种跨端、跨任务的复杂度，也无法按需扩展能力。

## 系统设计：三端 + 三层

**三端分工**

- **移动端**：灵感收集、收藏检索、工作流设计入口；关键操作的**任务审批**——手机是遥控器。
- **桌面端**：本地语音 ASR（类 Typeless，本地模型实时流式转写）、sandbox 内本地文件管理与 Co-work，不依赖云端的任务就地完成。
- **云端**：Main Agent 常驻、Core Agents 长期运行，打通浏览器、邮件、飞书 / Notion / GitHub 等生态。

**三层 Agent 架构（可插拔的核心）**

```
Main Agent（永远在线，接收所有输入）
  ├─ 简单请求 → 自己答
  ├─ 需要专家 → 调度对应 Core Agent
  └─ 端侧能处理 → 根本不上云
```

Core Agents 是一个**可插拔的专家角色池**：按任务类型动态调度不同专家 agent，新增能力等于往池子里加一个角色，而非重写主干。模型、服务、技能都按可替换的方式组织（可换模型 provider、可配外部服务、可装载 skill）。

## 为什么它重要

这是我对"agent 产品该长什么样"的一次完整回答：**模型之外的那层壳（入口、调度、审批、本地执行、生态连接）才是产品的主体**。它把 harness 的几个核心命题——context 装配、工具边界、权限审批、多 agent 编排、端侧/云端分工——落进了一个具体的架构里。

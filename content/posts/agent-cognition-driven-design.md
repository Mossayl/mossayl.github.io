# 通用 Agent 的设计陷阱：你以为在设计工具，其实在假设用户

大家都在讨论 human-in-the-loop。

怎么设计提问节点，怎么让用户在关键时刻介入，怎么在 AI 不确定的时候 ask questions。这些讨论没有错，但我觉得有一个更根本的问题被跳过了：

**你假设的那个"人"，到底是谁？**

---

## 一、用户不是铁板一块

设计 Agent 产品，最先要问的不是"给它什么工具"，而是"它在跟谁说话"。

**第一类：有经验的人。**

40 岁的后端工程师，20 年工程直觉。他知道什么叫可回滚、可测试，他清楚自己的决策边界在哪，他能看出一段代码里潜在的并发问题。

跟 AI 协作，他缺的不是被教，是更快的执行力和偶尔的外部视角。这时候 human-in-the-loop 是对的——他的判断比 AI 更可靠，让他介入是在引入更好的判断。

**第二类：正在成长的人。**

刚入门的大学生，算法或设计只学了一学期。他不知道什么叫时间复杂度的实际影响，不知道一个 UI 组件为什么视觉上"看起来不对"，不知道接口设计里有哪些隐藏的权衡。

现在的 AI 在这些领域比他更懂。这时候让他"人工介入判断"，并不是在引入更好的判断，是在引入更弱的判断。

让他先想清楚再告诉 AI，是在浪费他的时间，也是在拖慢 AI 能给他的帮助。

**第三类：与 AI 一起长大的人。**

7、8 岁，AI 是他们认知世界的基础设施之一。他们不是在"用工具"，是在用一种新的认知方式成长。对他们来说，AI 不是助手，是认知伙伴。

---

这三类用户，需要的 Agent 形态完全不同。

但今天大多数通用 Agent 产品，都隐含了一个默认用户——通常是第一类：有经验、能独立判断、能给出清晰指令的成年人。

这个假设，决定了很多功能的设计方向。也决定了为什么很多功能对第二类、第三类用户几乎没用。

---

## 二、human-in-the-loop 的真正问题：谁的 loop

Human-in-the-loop 本身没有问题。问题是：**谁** in the loop，**在哪个阶段** in。

通常的做法是在执行中设置提问节点：系统跑到某个地方，不确定了，ask user。这在风险确认、权限批准、真正需要用户偏好判断的地方是有价值的。

但还有一个更根本的阶段常常被忽略——**任务开始之前，问题本身有没有被想清楚。**

比如一个刚入门的用户说："帮我写一个用户登录的接口。"

如果 AI 比用户更懂这个领域，等用户"想清楚"是没有意义的——他不知道要考虑 token 有效期、不知道要考虑并发登录的处理、不知道要考虑密码存储方式。

这时候更好的做法是：AI 直接帮他把问题建模——"你需要考虑这几个问题，我给你一个合理的默认方案，你确认一下"——让他在更高的起点上开始，而不是等他自己从零摸索。

反过来，对那个 40 岁的工程师，他有自己的判断，他可能对某个技术选型有强烈的偏好，这时候 AI 反而应该多问——不是因为 AI 不懂，是因为他的判断在这里比 AI 更可靠。

**两种情况下，"让人介入"的含义完全不同。**

第一种，人在补 AI 的短板。

第二种，人在被自己的短板拖慢。

---

## 三、别把设计时间都花在"让人提问"上

这里有一个设计陷阱，我觉得很多产品都掉进去了。

花大量精力设计"ask your question"类工具——精心设计提问节点，精心设计追问逻辑，觉得这样就在做 human-in-the-loop，就在尊重用户判断。

但是，**提问系统在假设用户已经有足够的认知来回答。**

如果用户没有这个认知，提问只是在暴露他的盲区，却没有帮他填上。AI 停下来等他，他给出的答案反而让任务跑偏。

Anthropic 自己在 [Writing Tools for Agents](https://www.anthropic.com/engineering/writing-tools-for-agents) 里说了一个设计原则：不要只是把已有的 API 包一层——要**以 agent 的认知方式为中心**来设计工具，而不是以系统的架构为中心。

这个原则同样适用于用户侧：不要只是把"人工介入"做成一个通用的 ask-question 节点，要以**用户的认知状态**为中心来决定 AI 该怎么介入。

有时候，与其设计一套提问系统，不如先做一个 skill，直接上。

一个好的 skill，可以在用户认知不足的地方直接补位——不需要用户先知道该问什么，才能得到帮助。这是一种更主动的介入方式，但它的前提是你已经判断了：这个用户在这个领域，AI 的认知比他更可靠。

---

## 四、认知补位，而不是功能堆叠

Anthropic 的 "Building Effective Agents" 里有一句话我觉得说得很准：

> "find the simplest solution possible, and only increasing complexity when needed."

这句话通常被理解成工程上的简洁原则。但我觉得它对产品设计的含义更深：

**在你加下一个工具、下一个提问节点、下一个 routine 之前，先问自己：这是在解决问题，还是在绕过一个更根本的问题？**

能用 skill 解决的，不要训进模型。能前置建模的，不要靠 runtime 反复提问。工具设计过多，本质是在把复杂度转嫁给运行时，而不是在设计阶段解决。

更广义地说，通用 Agent 的产品设计，应该是**认知补位系统的设计**，而不是功能列表的设计。

用户认知充分的地方，Agent 是执行器。

用户认知有盲区的地方，Agent 是视角补充。

用户认知还没形成的地方，Agent 是认知脚手架。

这三种角色，对应完全不同的产品形态。把它们混在一起，或者全部设计成"执行器 + ask question"，是今天很多通用 Agent 产品的真正问题所在。

---

## 五、我们还没解决的问题

说到这里，我要诚实地说：上面这些判断，我们自己也还在摸索。

我们现在有两个 skill——Eileen 和 Grill-me——做的是前置理解这件事：在任务开始之前，帮用户把问题想清楚，提高任务表征的质量，而不是在执行中不断 ask questions。这是我们目前能给出的一个局部解法。

但更深的问题还没有答案：

通用 Agent 如何在整个交互过程中，持续感知用户的认知状态？如何判断这个用户现在是在哪个阶段、哪个领域的认知水平？如何动态决定自己该是执行器、该是视角补充、还是认知脚手架？

这些问题，今天没有人有完整的答案。

但我觉得，**这才是通用 Agent 产品设计真正值得投入的方向**——不是更多工具，不是更复杂的提问系统，而是对用户认知状态更准确的理解，和基于这种理解的动态介入。

人不是固定的。认知状态不是标签，是流动的。

一个 7 岁的孩子在成长，一个 40 岁的工程师在一个新领域也可能是初学者。通用 Agent 如果能感知这种流动，才算真的理解了"通用"是什么意思。

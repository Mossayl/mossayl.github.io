# Token Efficiency：比模型选型更重要的事

---

过去一个月，我在工作中烧掉了大约 3 万块的模型 API 费用。

这个数字本身不让我难受。让我难受的是：事后复盘，我意识到其中相当一部分是可以避免的——不是因为我用了错误的模型，而是因为我在错误的时间做了错误的事。

大家现在讨论 AI 效率，焦点几乎全在"用什么模型"。但我认为这个讨论还停留在表面。真正的问题不是模型选型，是**你在什么认知状态下启动了什么任务**。

---

## Token 的质量，比 token 的数量更重要

"token 效率"这个词，现在流行的理解是：同样的任务，花更少的 token 完成。

但这个定义太窄了。

更完整的理解是：**在认知匹配的情况下，用最低成本完成任务**。

这里有两个关键词：

**认知匹配**——你对任务的理解程度，决定了你能不能把对的信息用对的方式喂给模型。认知不到位，你会给模型错误的方向，然后用大量 token 在错误方向上跑，最后返工。

**最低成本**——不只是钱，还包括时间、注意力、以及你在错误路径上积累的"认知债"。

我那次烧掉的 3 万块里，最贵的部分不是 API 调用费，是我重复做了三次同一件事：造题。每次都以为自己想清楚了，每次都发现方向偏了，然后重来。

---

## Token 浪费的真实来源

复盘下来，token 浪费主要来自三个地方：

**1. 模型选型错位**

贵模型做执行是浪费，便宜模型做规划是返工。

这个道理说出来很简单，但实操中很难做到——因为大多数人没有在任务开始前就想清楚"这个阶段需要的是规划还是执行"。

规划/拓展阶段需要的是：帮你看到你没想到的角度，拓宽你的认知边界，把你已有的模糊想法拉清晰。这件事用便宜模型做，质量会显著下降。

执行阶段需要的是：按清晰的指令完成确定性任务。这件事用贵模型做，是在用火箭炮打蚊子。

**2. Prompt 密度不够**

同样一个任务，不同人写的 prompt 消耗的 token 数量可以差 10 倍，但产出质量差不多。

真正的效率高手能用更少的 token 把模型拉到正确方向——背后是他对模型认知结构的理解。他知道哪些信息是模型真正需要的，哪些是他自己的废话。

这个能力很难直接教，但有一个信号可以帮你判断：如果你经常需要说很多话才能让模型理解你要什么，大概率是你的任务 mental model 本身还不够清晰。

**3. Context 没有管理**

长 session 里，最贵的浪费是重复。你在第 10 轮对话里解释的背景，和你在第 2 轮里解释的背景，有多少是重叠的？

模型不记得，你每次都要重新喂。

真正的 context 效率是：把信息压缩进结构化的 memory 或 summary，而不是让模型一遍遍重新处理原始信息。

## 认知缺口才是真正的成本

## 认知缺口才是真正的成本：它分三层

把这三个来源合并来看，会发现一个统一的根因：

**认知缺口分三层，缺哪层，浪费的方式不同：**

- **模型认知缺口**：知道目标，但不知道用什么模型、怎么用——导致资源错配，花错了钱
- **实验认知缺口**：知道目标，但不知道怎么验证——导致在错的地方全力执行，最后返工
- **业务认知缺口**：不知道"做好了"长什么样——导致目标模糊，做完才发现方向偏

大多数人讨论 token efficiency，只想到了第一层。但我那次烧掉的大部分钱，来自第二层——实验认知的缺口。

**认知缺口的代价，是用 token 来填的。**

你对任务越不清楚，你就越需要通过大量的试错来摸清边界。每一次试错都在消耗 token。这些 token 不是在完成任务，是在建立你对任务的认知。

这不是说试错不应该发生——新任务本来就需要探索。问题是：**你是在执行成本最高的时候才开始探索，还是在最低的时候就把探索做完了？**

我那三次重复造题，每次都是在把整个流程跑完之后，才发现方向不对。最贵的探索方式。

---

## 旧坑和新坑

这里有一个区分值得单独说：**旧坑和新坑是完全不同的问题**。

旧坑——那些在同类任务中反复出现的问题——已经被大量的人踩过，记录过，被训进模型了。模型在这类问题上大概率比人更可靠。你不需要花太多 token 去探索，用 checklist 拦住就好。

新坑——新约束条件下的新问题——没有先验。有业务经验的人在这里同样没有优势，因为他的经验是基于旧约束的。

做一个新产品、新业务、新任务，20% 到 50% 的坑是历史经验覆盖不到的。这些坑只有两种处理方式：

**一是便宜地踩**：在资源消耗最小的时候，用最小的 scope 跑一个 spike，目的不是出结果，是提前暴露风险。

**二是借别人踩过的**：用好模型在执行前做一轮"预演"——让模型帮你搜索这个领域别人踩过的坑，把你感觉到的风险说清楚，让它帮你验证或者补充。

两种方式的共同前提是：**你得在开跑之前就意识到这些坑的存在**。

## 在动手之前，先做认知校准

这是我复盘之后养成的习惯，叫"preflight"——预飞。

任何新任务开始之前，强制回答四个问题：

**1. 完成标准是什么？**
"做好了"长什么样？谁来判断它达标了？

这个问题看似简单，但大多数人跳过了。没有清晰的完成标准，你不知道什么时候可以停，也不知道什么时候需要重来。

**2. 已知和未知的边界在哪里？**
这个任务里，我真正知道怎么做的部分是什么？完全没把握的部分是什么？

注意区分"真正知道"和"以为知道"——后者是最危险的，因为它会让你绕过应该做的验证。

**3. 高风险的未知在哪里？**
未知里，哪些可以靠模型预演提前规避？哪些只能设计实验暴露？

**4. 实验先于执行**
对每一个"只能实验暴露"的高风险未知，在全力执行之前，先用最小成本跑一次验证。

这四个问题不需要花太多时间——10 到 15 分钟的对话，用好模型做这个校准，然后再决定怎么执行。

这个阶段的 token 成本极低。但它能省掉的返工成本，可能是它自身成本的 10 倍。

## 一个还没人做的机会

我在想，未来会有一个 meta-agent 专门做这件事——不负责完成任务，只负责**决定用什么资源完成任务**。

它做的事情是：把一个模糊任务拆解成高智力子任务和机械执行子任务，给每个子任务分配合适的模型，管理 context 在子任务之间的流动，并在执行完成后判断结果是否值得升级复核。

这个 agent 现在还不存在，因为大家的注意力还在让 agent 更有能力上。但当 agent 能力到达某个阈值之后，resource allocation 会变成下一个核心问题。

到那时，真正的效率差距，不在于你用了什么模型，而在于你有没有一个机制，让每一个 token 都花在刀刃上。

你的认知越完整，你越能正确分配模型资源。认知缺口，永远是最贵的 token 来源。
